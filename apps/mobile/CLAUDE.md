# Mobile — convenciones

UI con **Tamagui 3**, nunca Mantine. Nueva feature: `/new-feature`.

## Estructura

```
apps/mobile/
  app/                    # Expo Router
    _layout.tsx           # Tamagui + SWRProvider + AuthProvider + BiometricsProvider + Notifications/Confirm/ActionSheet + AuthGate (Stack) + LaunchSplash
    login.tsx
    profile.tsx           # ruta de stack sobre las tabs (se abre solo desde la tarjeta de usuario de "Más")
    admin.tsx             # ruta de stack, solo ADMIN (se abre desde "Más")
    gym/index|plans|reorder.tsx  # rutas de stack de Gimnasio (se abren desde "Más"; sin tab bar)
    (tabs)/index|media|pantry|more.tsx
  src/
    core/auth/            # AuthProvider (sesión; los tokens se leen y escriben vía `@/shared/api`, módulo `tokenStorage`)
    core/authGate/        # AuthGate: spinner, ErrorState de sesión sin verificar o el Stack con rutas protegidas
    core/biometrics/      # BiometricsProvider (huella/rostro, bloqueo de arranque) y SensitiveGate (módulos sensibles)
    core/launch/          # LaunchSplash (animación de arranque) y su estado (`useLaunchDestination`)
    core/providers/       # SWRProvider (caché, reintentos, foco con AppState)
    core/serverWake/      # ServerWakeNotice (aviso de cold start)
    shared/api/           # API_KEYS, client Bearer, tokenStorage
    shared/ui/            # primitivas de UI (ver abajo)
    shared/navigation/    # FloatingTabBar, NAV_ICONS, NAV_HREFS, TAB_ROUTES, MORE_TAB y useRevalidateOnFocus (lo que depende de auth/router; shared/ui es presentacional)
    features/<name>/      # screen + hooks (ver abajo)
    theme/                # tamagui.config, fonts, elevation, gradient
    assets.d.ts           # tipos de las imágenes estáticas (`*.png`) que resuelve Metro
```

Estructura de features (la misma que web; árbol y reglas): [docs/architecture.md](../../docs/architecture.md#estructura-de-features-web-y-mobile).

- Scaffolding: `pnpm new-feature <name> --mobile` desde la raíz (ver `docs/mobile/new-feature.md`).
- Imports: `@/shared/api`, `@/shared/ui`, `@/core/auth`, `@/features/...`, `@/theme/...`.
- **Prohibido:** feature A → feature B.
- Contratos desde `@omni/shared/*`; no duplicar schemas.
- **React Compiler activo** en mobile (`experiments.reactCompiler: true` en `app.json`). Web no lo tiene activado.
- **Tamagui 3** (`tamagui` y `@tamagui/config` 3.3.3, exactas). El config (`src/theme/tamagui.config.ts`) parte del pack congelado `@tamagui/config/v5` (no el v6, que cambia escalas y colores) más el driver de animaciones de React Native (`@tamagui/config/animations-rn`: ningún config de v3 trae uno y los `transition` de los Sheet lo necesitan). El compilador ya no es `@tamagui/babel-plugin` sino `withTamagui` de `@tamagui/metro-plugin` en `metro.config.js` (mismos exports que `@tamagui/cli/metro`; se usa el paquete suelto porque `@tamagui/cli` fija `typescript@7` y pnpm lo propaga como peer de `typescript-eslint`, que no lo soporta), con sus opciones en `tamagui.build.ts`. `babel.config.js` queda solo con `babel-preset-expo`. El plugin pide como dependencias directas `metro` y `metro-resolver` (misma versión que trae Expo: se suben con él; `metro.versions.test.js` falla si difieren de las de `@expo/metro`) y la evaluación estática pide `@tamagui/core` y `@tamagui/web`: con el layout aislado de pnpm no se resuelven si no están declarados. Si cambia el config, `tamagui.build.ts` o la versión de Tamagui, el caché de Metro puede servir salida vieja: `expo start -c` (o `expo export --clear`).
- **Expo SDK 58** (React Native 0.88, React 19.3.0, Hermes V1 por defecto). `react-dom` está declarado en `devDependencies` con la misma versión exacta que `react`: expo, expo-router y tamagui lo piden como peer, y sin declararlo pnpm resolvía el `react-dom` de web (otra versión de React). `test-renderer` (peer de RNTL 14) va en la línea de la versión menor de React (`1.3` con React 19.3). `@react-native/jest-preset` (peer obligatorio de `jest-expo`) y `@react-native/metro-config` (peer de `react-native-worklets`: sin declararlo, pnpm lo resolvía con una versión vieja) van con la misma versión exacta que `react-native`: se suben juntos. `@expo/dom-webview` está declarado (`expo install`) porque es peer de `@expo/log-box` y pnpm lo dejaba en la versión del SDK anterior. `metro` y `metro-resolver` también están en `expo.install.exclude`: `expo-doctor` de SDK 58 espera Metro ^0.84.6, pero el CLI de Expo 58 bundlea con el Metro 0.87.1 de `@expo/metro`, que es el que tienen que igualar (ver `docs/mobile/tooling.md`). `typescript` queda en 5.9.3 y está en `expo.install.exclude` (`package.json`): con la 6.0.3 que pide el SDK, `tsc` deja de cargar `@types/jest` solo y `check-types` falla en todos los tests. `eslint-config-expo` (desde 57) trae las reglas del React Compiler de `eslint-plugin-react-hooks` 7 y quedan todas activas: un caso que no se puede reescribir lleva `eslint-disable-next-line react-hooks/<regla>` en la línea, nunca un apagado global. Hoy no queda ninguno (#303): el estado derivado se calcula en el render (`SensitiveGate`) o en un reducer (`useSheetQueue`), no en un efecto que escribe estado. Hermes V1 (el motor por defecto desde SDK 56): SDK 56 tenía una regresión de memoria con reanimated/worklets que SDK 57 corrige, así que SDK 56 no se publicó. En el dev client el PSS sigue creciendo unos 4 MB por minuto en reposo (debugger y DevTools); en el APK de release queda estable (en el login: ~210 MB en SDK 57 con Tamagui 2 y entre 150 y 158 MB en SDK 58 con Tamagui 3, medido durante 3,5 minutos), así que la memoria se mide siempre en release.
- **Tokens:** SecureStore vive en `src/shared/api/tokenStorage.ts` (una sola clave con access y refresh). Solo `tokenStorage`, `rememberedUser`, `biometricPreference` y el respaldo del clima (`shared/api/lastWeather.ts`, clave `omni.lastWeather.<usuario>`: solo el dato del contrato, sin coordenadas) y el último plan de gimnasio abierto (`shared/api/lastGymPlan.ts`, clave `omni.gym.lastPlan.<usuario>`: solo el id; `AuthProvider.clearSession` borra los dos al cerrar o perder la sesión) y la pista de tema (`shared/api/colorSchemeHint.ts`, clave `omni.colorSchemeHint`: el tema del perfil de la última sesión, para el primer cuadro; la escribe y la borra `useProfileColorScheme`) hablan con `expo-secure-store`.
- **Cambio de tema (#294):** `ColorSchemeProvider` captura la pantalla con `react-native-view-shot`, aplica el tema nuevo debajo y desvanece la captura en `THEME_FADE_MS` (si la captura falla o no carga, o con movimiento reducido, el cambio es instantáneo). `react-native-view-shot` es dependencia nativa: agregarla o actualizarla pide rebuildear el dev client y el APK.

## Navegación

- **Acceso por sesión (#332):** `AuthGate` usa `Stack.Protected`. Con sesión (y sin bloqueo biométrico) están las rutas de `SESSION_ROUTES`; sin ella, solo `login`, y el router pasa solo de una a otra. **Toda ruta nueva de `app/` que pida sesión va en `SESSION_ROUTES`** (`core/authGate/AuthGate.tsx`): una que falte queda abierta sin sesión, y un test de `AuthGate` compara la lista con `app/`. No redirigir con `<Redirect>` desde fuera de un navegador: expo-router reemplaza su ruta raíz y vuelve a montar toda la app.
- Tabs **Inicio · Media · Alacena · Más**, sin header (`headerShown: false`): cada pantalla arranca con `Screen` + `ScreenHeader` (Inicio es la excepción: una sola card con el saludo, como web). Perfil (`/profile`, ruta de stack, también sin header nativo) se abre **solo desde Más** y su `ScreenHeader` lleva el botón de volver (`onBack`): los headers de las tabs no llevan avatar. Perfil incluye la tarjeta "Seguridad" (toggle de huella / rostro, solo si el teléfono tiene biometría enrolada) y la tarjeta "Foto de perfil" (`expo-image-picker`: JPG/PNG/WebP de hasta 2MB, se sube al elegir y "Quitar foto" la borra; el `FormData` del PUT (`buildAvatarForm`) lleva el archivo como `File` de `expo-file-system` (acepta `file://` y `content://`, y `expo/fetch` lo serializa solo); si no existe o no se puede abrir, falla con `AVATAR_READ_ERROR` antes del request. `expo-file-system` es dependencia nativa: agregarla pide rebuildear el dev client; el selector del sistema no pide permisos nativos, así que `app.json` no necesita el plugin, #39) y la fecha de nacimiento como texto enmascarado dd/mm/aaaa.
- **Sin `@react-navigation/*`:** expo-router 57 ya no depende de React Navigation y trae lo que usamos: `useIsFocused`, `ThemeProvider`, `DarkTheme`, `DefaultTheme` y `Theme` de `expo-router/react-navigation`, y `BottomTabBarProps` de `expo-router/js-tabs`. No sumar `@react-navigation/*` al `package.json`.
- Labels, rutas y disponibilidad salen de `NAV_REGISTRY` de `@omni/shared/navigation` (el mismo que usa el navbar de web); los íconos, de `NAV_ICONS`. Tabs: `MOBILE_TAB_KEYS`.
- "Más" es el launcher: tarjeta de usuario → Perfil, toggle de tema (override de la sesión; el Switch lee `selectedScheme`), módulos (los que no tienen `"mobile"` en `availableOn` salen con el `Badge` "Próximamente"), Administración si el rol es ADMIN (`/admin`, ruta de stack con `onBack`; `AdminScreen` redirige a Inicio si el rol no es ADMIN, como `AdminRoute` de web) y cerrar sesión (que solo está acá, no en Perfil; Perfil tiene "Cerrar sesión en todos los dispositivos").
- Módulo nuevo en mobile: sumar `"mobile"` a su `availableOn`, crear la ruta en `app/` con el mismo `path` y registrarla en `NAV_HREFS` (`src/shared/navigation/navHrefs.ts`, tipada con `typedRoutes`).

## Arranque

La splash nativa (`expo-splash-screen` en `app.json`) queda hasta que `LaunchSplash` (`core/launch`, montado en `app/_layout.tsx` entre `AuthGate` y `ServerWakeNotice`) pinta su primer cuadro, que es igual: mismo fondo según el **sistema** y mismo logo de 200 dp (el test del componente compara las dos cosas con `app.json`). La espiral acelera, gira mientras se verifica la sesión (por encima del spinner de `AuthGate`) y, con la destino lista y un mínimo de 800 ms, crece hacia su centro y se desvanece en 400 ms. Con "reducir movimiento" queda quieta y solo hace un fundido de 250 ms. La destino avisa con `useLaunchDestination(ready)`: `AuthGate` (ruta de la app con sesión o `ErrorState` de sesión sin verificar) y `LoginScreen` (con el usuario recordado ya leído). **Una pantalla nueva en la que pueda desembocar el arranque fuera de ese `Stack` tiene que avisar también**: si no, la animación recién cierra por el tope de `useLaunchDeadline` (3 s desde que la sesión y la biometría quedan resueltas; la verificación de la sesión no tiene tope). Atrás se consume solo si hay historial; si no, sale de la app. El estado vive a nivel de módulo: corre solo en el arranque en frío. Mientras dura, `ColorSchemeProvider` aplica el tema sin el fundido de #294 (`instant`). Lo que al montar abra un diálogo del sistema (hoy, el permiso de ubicación de `useDeviceLocation`) espera a `useLaunchState().finished`: si no, sale sobre la animación.

## API paths

Todos los endpoints en `API_PATHS` de `@omni/shared/api` (el mismo mapa que web); `src/shared/api/keys.ts` lo re-exporta como `API_KEYS`.

```ts
import { api, API_KEYS } from '@/shared/api';
await api.get(API_KEYS.media.list);
```

Base URL: `EXPO_PUBLIC_API_URL` (sin slash final). **Prohibido:** literales `'/api/...'` fuera de ese mapa. Verificación: `pnpm --filter mobile check-api-paths`.

El núcleo HTTP (request, 401 → refresh single-flight → reintento, parseo de errores y 204) es `createApiClient` de `@omni/shared/api`. `src/shared/api/client.ts` es el adaptador: `getAuthHeaders` con el Bearer de `tokenStorage`, el refresh con `{ refreshToken }` y `logoutSession` (que espera al refresh con `waitForRefresh`).

## Cold start de la API

Igual que web: el client usa `fetchWithWake` (`shared/api/serverWake.ts`) en `request` y en el refresh, con `API_KEYS.health`. Reintenta si la respuesta es del proxy o de la plataforma (no es JSON y trae 502/503/504 o `text/html`: cualquier método; un JSON, aunque sea 502, se devuelve tal cual) o si `fetch` lanza un error de red solo en GET/HEAD/PUT/DELETE; en POST/PATCH el error se propaga porque no se sabe si la API procesó el request. Un 504 del proxy en POST/PATCH tampoco se reintenta (lanza `ApiError` 504). Cada intento tiene tope hasta los headers (el `fetch` global es `expo/fetch` desde SDK 56, y usa el mismo cliente OkHttp de RN, que no tiene timeout): 30 s si es idempotente, 100 s en POST/PATCH (esperan el cold start); al vencer, `ApiError` con status 0. El refresh se pide con `{ idempotent: true }` (la API acepta el mismo token dentro de su gracia de rotación): corta a los 30 s y se reintenta, así un refresh colgado no bloquea los requests que lo esperan. Sin conexión no espera 90 s: tras 2 sondeos seguidos al health con error de red (no por su timeout) y sin ninguna respuesta HTTP previa, corta, sin banner, y relanza el error de red del request (no hay NetInfo: no se consulta el estado de red del dispositivo); una respuesta del proxy (502/503/504, HTML) o un timeout del sondeo siguen el polling. Además, `ServerWakeNotice` (`core/serverWake`, montado en `app/_layout.tsx`) muestra un `Banner` mientras la API despierta (aparece cuando falla el primer sondeo o pasan ~1,5 s sin respuesta). Cualquier POST/PATCH (no solo el login) que pasa 1,5 s sin headers sondea el health en paralelo (sin reintentarse) para encender el aviso, y uno que sale con un sondeo en curso lo espera antes de enviarse (hasta 90 s). `LoginScreen` llama a `ensureServerAwake()` al montar, así la API despierta mientras el usuario escribe; el POST del login espera ese sondeo si sigue en curso, y los campos (el ojo incluido) quedan deshabilitados mientras carga. `serverWake.ts` es una instancia de `createServerWake` de `@omni/shared/server-wake`, que tiene la orquestación compartida con web, las constantes y la decisión pura.

## Hooks (SWR)

```ts
import { api, API_KEYS, buildQueryString, fetcher } from '@/shared/api';
import useSWR from 'swr';
import useSWRImmutable from 'swr/immutable';
```

| Caso            | Hook                                                |
| --------------- | --------------------------------------------------- |
| Sesión / perfil | `useSWRImmutable` + key null si no hay token        |
| Listas / search | `useSWR`                                            |
| Mutations       | `api.post/patch/delete` + `mutate` / `globalMutate` |

Un hook por archivo en `hooks/` de la feature (`hooks/useX.ts`), nombre de función = nombre de archivo. Return: dominio + `isLoading` + `error` (+ `isMutating` si aplica). Paridad de patrones con web: skill `swr-hooks`.

`SWRProvider` (`core/providers`, por encima de `AuthProvider`: la sesión y los datos comparten caché) usa una caché a nivel de módulo, porque una creada al montar se perdería si el layout raíz se volviera a montar; pone el `fetcher`, los reintentos (`SWR_RETRY_OPTIONS` de `@omni/shared/api`, igual que web: 3, sin reintentar 4xx salvo 408 y 429) y `initFocus` con `AppState`: los `useSWR` revalidan al volver a primer plano, los `useSWRImmutable` no. Sin NetInfo no hay `initReconnect`. Las listas y el perfil llevan "tirar para actualizar" con `usePullToRefresh(refresh)` de `@/shared/ui` (`refreshControl`).

## Auth

- **No cookies.** Tokens en `expo-secure-store` vía `tokenStorage`, en **una sola clave** (`omni.session`, JSON con access y refresh): `setTokens` los escribe juntos o no escribe nada. `tokenStorage` migra una vez por proceso las claves anteriores (`omni.accessToken` / `omni.refreshToken`) sin cerrar la sesión; los tests de `tokenStorage` cubren que sea idempotente. Los tokens se leen siempre por `tokenStorage`, nunca con `SecureStore` directo. El par de JWT ronda los 600 bytes (la API firma `sub`, `username` y `role` en el access, y `sub` y `jti` en el refresh): si se suman claims o se soporta iOS, `expo-secure-store` avisa a partir de ~2048 bytes por valor.
- **Usuario recordado:** tras un login exitoso `LoginScreen` guarda solo el nombre de usuario (`rememberedUser.ts` en `shared/api`, clave `omni.rememberedUser`; nunca contraseña ni tokens, y fuera de `tokenStorage`). Con uno guardado el login muestra avatar, saludo y solo la contraseña (con el teclado abierto el hero se compacta en una línea, en las dos variantes); "Ingresar con otro usuario" lo borra. Cerrar sesión no lo borra.
- **Biometría (#173):** `expo-local-authentication` (plugin en `app.json` con `faceIDPermission`: agregarlo o actualizarlo pide rebuildear el dev client). Todo vive en `core/biometrics`: `BiometricsProvider` (en `_layout`, dentro de `AuthProvider`) lee del sistema si hay biometría usable (hardware + algo enrolado; se relee al volver a primer plano) y de qué tipo (`BiometricKind`: huella / rostro / ambas / genérica; `biometricNoun` adapta los textos), y guarda la preferencia **por dispositivo** en SecureStore (`biometricPreference.ts`, clave `omni.biometricEnabled`, solo un `1`; no viaja con el perfil de la API porque la huella o el rostro enrolados son del teléfono y el login la necesita antes de tener sesión). `enabled` = preferencia + disponible; sin biometría en el teléfono no se muestra nada (Perfil, login ni gate). No guarda contraseña ni tokens propios: solo libera la sesión que ya guarda `tokenStorage`, que sigue siendo la que autenticó el servidor. Dos usos independientes: **(1) bloqueo de arranque** (`locked`): con la biometría activada la app abre bloqueada; con sesión guardada `AuthGate` deja solo el login, donde `LoginScreen` ofrece "Ingresar con huella / rostro" como acción principal (la contraseña queda debajo; cancelar o fallar deja la contraseña, que autentica contra el servidor y también libera el bloqueo vía `markUnlocked`). Sin sesión (después de cerrar sesión) no hay nada que liberar y el botón no aparece. "Ingresar con otro usuario" siempre desactiva la biometría del dispositivo (la preferencia no se hereda a la persona siguiente) y, con el bloqueo puesto, cierra antes la sesión guardada (si no, saltearía la biometría). **(2) módulos sensibles**: `<SensitiveGate module="expenses">` (envuelve la pantalla; `SENSITIVE_MODULES` en `biometrics.ts` es la lista en código: Gastos y Gastos compartidos, que todavía no existen en mobile) pide biometría al entrar si pasaron más de `SENSITIVE_UNLOCK_TTL_MS` (5 min) desde el último desbloqueo o si la app pasó por `background`, y se vuelve a evaluar al recuperar el foco de la pantalla (las tabs quedan montadas; `useIsFocused`) (`inactive`, que es lo que dispara el prompt de Face ID en iOS, no cuenta). Ahí el sistema también ofrece el PIN o patrón del teléfono como alternativa. Toggle en Perfil: `SecurityCard`, que al activar pide una verificación biométrica y solo entonces guarda. Tests con `@/test/localAuthenticationMock` (`jest.mock('expo-local-authentication', () => jest.requireActual('@/test/localAuthenticationMock'))`; `resetLocalAuthentication()` lo deja como un teléfono con huella enrolada).
- Login/refresh devuelven `accessToken` + `refreshToken` en el body (`AuthTokensResponse`).
- Cada request: `Authorization: Bearer <access>` y `X-Client: mobile` (`CLIENT_HEADER`, `src/shared/api/client.ts`). Con ese header la API emite un refresh token de 90 días que se renueva en cada refresh: la sesión vence solo tras 90 días sin abrir la app.
- 401 → refresh con `{ refreshToken }` → reintento. Lo maneja el client: no reimplementar en cada hook. Un solo refresh a la vez; si el access ya cambió cuando llega el 401 (otro request refrescó antes), reintenta sin rotar de nuevo.
- Solo un **401/403 del refresh** limpia los tokens y avisa (`setOnAuthFailure` → `AuthProvider.clearSession`). Un 5xx, un 429 o un error de red propagan el error y conservan la sesión: el `ApiError` que llega al hook es el del refresh, no el 401 original. Si la sesión cambió mientras el refresh volaba (logout, login nuevo), su resultado se descarta. Los hooks de datos reintentan un 429 y no los demás 4xx.
- Logout: `logoutSession()` del client espera un refresh en curso (hasta 3 s), lee el refresh token vigente al enviar y hace `POST` con `{ refreshToken }` sin pasar por el refresh por 401 (la API no responde 401 al logout); sin refresh token guardado no hace ningún request. `AuthProvider.logout` limpia tokens y caché de SWR aunque falle el POST, y al POST lo espera hasta 8 s (con la API colgada no espera su tope de 100 s); si falla el borrado en SecureStore, la UI igual sale de la sesión y el error se relanza para que quien llama avise (`MoreScreen` y `ProfileScreen` ya lo hacen).
- "Cerrar sesión en todos los dispositivos" (Perfil, con `confirm()`): `AuthProvider.logoutAll` hace `POST /auth/logout-all` con el access token y recién si la API responde limpia la sesión local; si el POST falla, propaga el error y la sesión queda abierta. Si la API confirmó pero falla el borrado en SecureStore, la sesión local igual se cierra y lanza `LocalSessionClearError`: `ProfileScreen` avisa con `notifyWarning`, porque las sesiones ya se cerraron.
- Al arrancar con token, si `/auth/profile` falla por red, timeout, 5xx, 408 o 429 (`isSessionUnverified`), `AuthGate` muestra un `ErrorState` con "Reintentar" (`retrySession`) y "Cerrar sesión" en vez de mandar al login: la sesión puede seguir siendo válida. Un 4xx que no sea 408 ni 429 sí manda al login. El hook de sesión recibe `SWR_RETRY_OPTIONS` directamente. `login()` cachea la sesión con `globalMutate` antes de activar la key, así no pide el perfil de nuevo.
- Errores al usuario: `getErrorMessage(err, fallback)` (de `@omni/shared/api`, re-exportado por `@/shared/ui`) muestra `err.message` solo si es `ApiError` (ya en español); un error de red o de parseo usa el fallback.
- Web usa cookies; no mezclar estrategias en el mismo client.

- Medidas: `RADIUS` / `SPACING` / `FONT_SIZE` de `@omni/shared/theme` como números (`padding={SPACING.md}`); sombras con `elevation('sm')` de `@/theme/elevation`. No usar tokens numéricos de Tamagui como medida (`padding="4"`, `gap="2"`, `borderRadius="4"`) en código nuevo (ver `docs/design-system.md`). La prop `size` de los componentes de Tamagui (`<Switch size="xl">`, `<Paragraph size="2">`, `Spinner`) es otra cosa: elige una variante del componente (alto, padding y fuente juntos) y se sigue usando. Con Tamagui 3 los tamaños de los controles son nombres (`xs`…`xl`), no tokens.
- Colores: tokens de tema **sin `$`** (`accentSurface`, `destructive`, `border-color`, …) en props de Tamagui; para valores crudos (íconos Phosphor, gradientes), `useSemanticColors()` de `@/core/theme`. Las claves compuestas de Tamagui van con guiones (`background-press`, `border-color`, `placeholder-color`); las propias de `SEMANTIC` siguen en camelCase. Los estados de interacción van en el valor de la propiedad que cambian, no en objetos: `opacity="press:0.7"`, `backgroundColor="background press:background-press"`, `borderColor="border-color focus:primary"`. `pressStyle`, `hoverStyle` y `focusStyle` ya no existen en Tamagui 3 y no fallan: se ignoran en silencio. Una cadena con cláusulas se arma con un valor sin espacios (un `rgba(0, 0, 0, 0.5)` con espacios se parte) y `buttonStyles.withPress(base, press)` arma el caso `base press:press`. `lineHeight` numérico es un factor, no píxeles: en píxeles va como cadena (`lineHeight="20px"`, ``lineHeight={`${LINE_HEIGHT.xl}px`}``). `defaultProps` del config no existe: el placeholder, el cursor y la selección del `Input` los fija `TextField`.
- Las features usan las primitivas: ESLint (`eslint.config.mjs`, con test en `eslint.config.test.js`) prohíbe importar `Button`, `Input` y `Switch` de `tamagui` en `src/features` y `app`, `Paragraph`, `Spinner` y `Alert.alert` en cualquier archivo, un feature que importe otro y los hex o colores nombrados fuera de tests. Feedback: `notify*`; confirmar: `confirm()`; elegir: `actionSheet()`.
- **Alacena** (`features/pantry`): dos pestañas (Inventario / Lista de compras) en `PantryScreen`; cada vista es una `FlatList`/`ScrollView` con el encabezado adentro. Los avisos de éxito de una hoja se encolan con `useSheetNotice` y salen al cerrarla. Filtros, schema del form, split de la lista e `isPantryKey` vienen de `@omni/shared/pantry`. "Escanear código" (`ScanSheet`, #260) usa `expo-camera` (`CameraView` con EAN-13, EAN-8 y UPC-A; plugin en `app.json` con `recordAudioAndroid: false`, así que agregarlo o actualizarlo pide rebuildear el dev client). Escanea primero (`POST …/products/scan`) y solo con un 404 consulta el código; `scanGate` evita sumar dos veces el código que sigue a la vista. El alta que llega del escaneo reusa `ProductForm` dentro de la misma hoja (dos `Modal` apilados no se usan). Contrato y estados en `docs/api/pantry-barcode.md`. `app.json` bloquea `RECORD_AUDIO` (`blockedPermissions`): `expo-image-picker` es un plugin legacy que `expo prebuild` aplica solo aunque no esté en `plugins`, y con sus opciones por defecto pide el micrófono, que la app no usa; una feature que lo necesite tiene que sacarlo de esa lista.
- **Gimnasio** (`features/gym`, #317): rutas de stack `/gym` (el plan abierto), `/gym/plans` ("Tus planes", paginada con `useSWRInfinite`) y `/gym/reorder` (orden de un día con flechas). Se abre desde "Más"; el último plan visto se guarda por usuario en `shared/api/lastGymPlan.ts` (solo el id). Los menús (plan, día, ejercicio) son `actionSheet()` con `destructive`; las confirmaciones, `confirm()`. - Un formulario en bottom sheet que tiene que tapar las tabs (p. ej. `AddMediaSheet`) va dentro de un `Modal` de RN con el `Sheet` sin `modal`, su `SheetOverlay` (scrim) y su `SheetFrame` de `@/shared/ui` (radio 32, grabber y sombra `sheet`): el portal de Tamagui (`<Sheet modal>`) crashea en Fabric con "The specified child already has a parent". El `Sheet` de Tamagui 3 avisa con `onTransition` (no con `onAnimationComplete`) y no siempre llega al cerrar, así que el `Modal` se oculta con un tiempo fijo (`SHEET_EXIT_MS`); mientras está visible tapa los toasts, por eso el error va en un `Banner` adentro y el éxito se avisa al cerrar.

## Botones de acción

A diferencia de web (alineados a la derecha), en mobile van **centrados y full-width**, apilados verticalmente cuando hay más de uno — así se maximiza el área de toque. El `Button` de `@/shared/ui` ocupa solo su contenido, como en Mantine: el ancho completo se pide con `fullWidth`. Sin `fullWidth`, `Button` y `Badge` se alinean al inicio (`alignSelf="flex-start"`); en una fila centrada se pasa `alignSelf="center"`.

- Un solo botón (guardar, actualizar) → `<Button fullWidth>`. El texto va como `children` (string) y la carga con `loading`, nunca un `Spinner` adentro.
- Confirmar + cancelar: **confirmar arriba** (filled), **cancelar abajo** (`variant="outline"`). `confirm()` de `@/shared/ui` ya lo hace así.
- Acciones destructivas standalone (ej. "Eliminar cuenta") siguen siendo filled (`color="destructive"`), igual que en web.
- **Deshabilitado hasta que haya cambios:** un botón de guardar de formulario (`Guardar cambios`, `Cambiar contraseña`) va `disabled` mientras no haya nada que enviar (campo distinto del guardado, o algo escrito). Las validaciones corren al enviar, con el error debajo de cada campo.
- **Preferencias que guardan al instante** (Switch, `SegmentedControl` de Tema en Perfil): muestran el valor nuevo enseguida, ignoran un segundo cambio de la misma preferencia mientras hay un PATCH en vuelo y, si falla, vuelven al valor anterior con `notifyError`. No llevan botón.

## Tests

- `jest-expo` (Jest 30) + `@testing-library/react-native` 14 sobre `test-renderer` 1.3 (reemplaza a `react-test-renderer`, que ya no está). Archivos `*.test.ts(x)` al lado del código, nunca dentro de `app/` (Expo Router los tomaría como rutas).
- En RNTL 14 `render`, `renderHook`, `fireEvent`, `act`, `rerender` y `unmount` son async: siempre con `await`. Como `await render(...)` vacía las actualizaciones pendientes, un estado intermedio (`isLoading`, "locating", un reintento en curso) solo se ve si la promesa que lo sostiene sigue pendiente: el test la deja colgada con un `new Promise` y la resuelve con `await act(async () => resolve(...))` después de la aserción. Un error al montar se prueba con `await expect(render(...)).rejects.toThrow(...)`.
- Test Renderer solo ve componentes host: no hay `UNSAFE_getByType`/`UNSAFE_getByProps`. Para lo que no tiene rol, texto ni label (el `Modal` de RN, el `RCTScrollView` con su `refreshControl`, las props que el doble de Tamagui pasa al `View`) están `getByHostType`/`queryAllByHostType` y `getByHostProps`/`queryAllByHostProps` de `@/test/hostQueries`. "Tirar para actualizar" se prueba con `userEvent.setup().pullToRefresh(getByHostType('RCTScrollView'))`.
- SWR solo vuelve a renderizar por los campos que se leyeron durante el render, y un `renderHook(() => useSWR(...))` los lee después (`result.current.data`): esos tests envuelven la respuesta con `trackSWR` de `@/test/swr`. Los hooks de la app que desestructuran `data`/`error`/`isLoading` no lo necesitan.
- Lógica pura (reducers de cola, helpers de tema) se testea sin renderizar. Para primitivas y providers, mockear `tamagui` con el doble compartido y probar el comportamiento (role, label, estado, callbacks), no el componente de Tamagui:

  ```ts
  jest.mock('tamagui', () => jest.requireActual('@/test/tamaguiMock'));
  jest.mock('@/core/theme', () => jest.requireActual('@/test/themeMock'));
  ```

  Los Stacks interactivos llevan `accessible` (si no, ni TalkBack ni `getByRole` los encuentran cuando están deshabilitados).

  El doble tiene `Sheet.Container` y `Sheet.Background`; `mockSheet.props` se actualiza en un efecto (disponible tras `render` o `act`) y `onTransition` es el callback de cierre. Para ver Tamagui de verdad (valores planos, themes, Switch, Input, Sheet con el config de la app) está `src/theme/tamagui.render.test.tsx`, sin mock.

- El compilador de Tamagui corre en Metro (dev y build de release), no en Jest: los tests ven siempre los componentes sin aplanar y los `// tamagui-ignore` que había en 15 pantallas ya no hacen falta (si un archivo necesitara apagarlo para el bundle, va como **primera línea**). Su consumo de memoria y cómo probar el bundle de producción están en `docs/mobile/tooling.md`. `jest.config.js` suma una transformación para `.mjs`: los paquetes de Tamagui 3 publican ESM en `.mjs`.
- Tests que tocan tokens (`tokenStorage`, client, `AuthProvider`): `jest.mock('expo-secure-store', () => jest.requireActual('@/test/secureStoreMock'))` (store en memoria; `store` para sembrar y verificar claves) y `global.fetch` mockeado. `tokenStorage` y el client guardan estado de módulo: en tests que lo necesiten, `jest.resetModules()` + `require`.
- Si un paquete de `node_modules` publica ESM sin build CommonJS, sumarlo a `transformIgnorePatterns` en `jest.config.js` (los `.mjs` ya se transforman). `nanoid` está ahí por eso: expo-router lo usa y el override `nanoid` de `pnpm-workspace.yaml` lo resuelve a la v6, que es solo ESM (sin él, `MoreScreen.test.tsx` falla con `Cannot use import statement outside a module`).
- Los tests que dependen del foco de la pantalla mockean `useIsFocused` con `jest.mock('expo-router/react-navigation', () => ({ useIsFocused: () => mockFocused }))`.
- `jest.setup.js` (`setupFiles` de `jest.config.js`) mockea `react-native-worklets` con su mock oficial (`react-native-worklets/src/mock`): sin eso, todo test que cargue Reanimated o expo-router falla con "Native part of Worklets doesn't seem to be initialized". También mockea `react-native-reanimated` con `@/test/reanimatedMock` (lo que usan `AuthBackground` y `useReduceMotion`): Reanimated 4.7 no carga en el entorno de Jest de RN, ni la versión nativa (pide `setCSSEventHandler`, que su módulo JS no tiene) ni la web de `react-native-reanimated/jest/resolver`, que necesita `document`. Si la app empieza a usar otra API de Reanimated, se suma al doble.
